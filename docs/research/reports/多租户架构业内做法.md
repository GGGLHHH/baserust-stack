# 用成员关系和 RLS 撑起单机多租户

> 调研日期：2026-11-25。依据 `docs/research/research_notes/多租户架构业内做法/` 下四份笔记（身份建模、PostgreSQL 隔离、框架模式、生命周期与运维），外加对本仓库代码的现状核对。引用标「二手」或「摘要」的条目，原笔记没能逐字核对一手页面。

到 2026 年，单实例多租户在业内已经有一套成形的默认组合，三个待决问题都能从中找到答案。身份层采用「全局账号 + 组织成员关系（membership）」：一个人只有一个账号，通过成员关系加入零到多个组织，角色挂在成员关系上。access token 只带**一个当前组织**，切换组织就是重新签一张 token。Auth0、Clerk、WorkOS、Logto 都这样做，Keycloak 26 也把 Organizations 转为正式功能。数据层在单个 PostgreSQL 实例上采用「共享表 + `tenant_id`」，PostgreSQL 行级安全（RLS）只当兜底；schema-per-tenant 在 2025–2026 年的厂商文章里普遍被降为「几百个租户以内才考虑」，database-per-tenant 的优势在单实例上基本拿不到。框架层的共识是「入口解析一次租户，在执行流里传递，跨进程时显式写进消息，没有租户就报错或返回空」。

落到 baserust，建议如下：租户表、成员关系、租户内角色放进 **idm**，因为签 token 的是 idm，而 app 不查 idm 库；租户的业务配置放 app。账号与租户**按多对多建模**，产品上可以先限制每人一个租户。数据用**共享表 + 仓储方法显式传 `tenant_id` + 事务级 `set_config` 的 RLS 兜底**。最紧迫的风险不在隔离模型的选择，而在两处现状：**运行时 role 同时是表的 owner**，以及 **nil UUID 被当作租户值使用**。前者让 RLS 默认失效，后者是「静默落到默认租户」的隐患。

## 身份层已收敛到「全局账号 + 成员关系」，切换租户就是换一张 token

各家 IdP 分成两派。**硬隔离派**给每个租户一套独立用户池，用户只属于一个租户，代表是 Keycloak realm、Cognito 的 user-pool-per-tenant、Entra tenant、Casdoor 和 Zitadel 的 organization。Keycloak 文档写的是「A user belongs to and logs into a realm」，realm 之间完全隔离（[Keycloak Admin Guide](https://www.keycloak.org/docs/latest/server_admin/index.html)）；Zitadel 写的是「Users exist within one organization」，而且用户不能在组织间迁移（[Zitadel users](https://zitadel.com/docs/concepts/structure/users)）。**成员关系派**只有一个全局用户池，组织是用户之上的一层。Auth0 写的是「A user can have one identity and be a member of several organizations」（[Auth0 Organizations](https://auth0.com/docs/manage-users/organizations/organizations-overview)），WorkOS 写的是「Users are global」，成员关系有 `pending` / `active` / `inactive` 三种状态（[WorkOS](https://workos.com/docs/authkit/users-organizations)）。2024–2026 年新做的 B2B 身份产品基本都选了后者。连 realm 派的代表 Keycloak 也在 **26.0（2024-10）把 Organizations 转为正式功能**，官方定位是「multi-tenancy within a realm」，模型为「Users belong to the realm first and can be members of zero or more organizations」（[Keycloak 26.0.0](https://www.keycloak.org/2024/10/keycloak-2600-released)；[Keycloak 博客](https://www.keycloak.org/2024/06/announcement-keycloak-organizations)）。终端产品也一样：GitHub、Slack、Linear、Notion 都是一个登录身份对应多个组织或工作区，界面上有明确的切换器（[GitHub](https://docs.github.com/en/organizations/collaborating-with-groups-in-organizations/about-your-organization-dashboard)；[Linear](https://linear.app/docs/workspaces)）。Azure 架构中心也建议尽量「single identity per person」，理由是 IdP 的很多威胁防护都建立在「一人一个账号」之上（[Azure Identity](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/identity)）。

两派在「登录时怎么定租户」上的差别是结构性的。硬隔离派必须在登录**之前**知道租户，否则不知道该查哪个账号，所以 Cognito 的 pool-per-tenant 要自己做入口路由，Casdoor 用 `/login/<org>` 路径（[Cognito](https://docs.aws.amazon.com/cognito/latest/developerguide/bp_user-pool-based-multi-tenancy.html)；[Casdoor](https://casdoor.ai/docs/organization/overview/)）。成员关系派可以**登录后**再定租户，主流组合是三步：先输邮箱（identifier-first），再用已验证的邮箱域名映射到组织（home realm discovery，简称 HRD），属于多个组织时再让用户选。Auth0 官方的说法是「Most organizations should choose Prompt for Credentials」（[Auth0 login flows](https://auth0.com/docs/manage-users/organizations/login-flows-for-organizations)）。WorkOS 在用户属于多个组织时返回 `organization_selection_required`，带一个 `pending_authentication_token` 和组织列表，前端选完再完成认证（[WorkOS errors](https://workos.com/docs/reference/authkit/authentication-errors)）。Keycloak 的做法是登录过程中提示用户选择（[Keycloak claims](https://github.com/keycloak/keycloak/blob/main/docs/documentation/server_admin/topics/organizations/mapping-organization-claims.adoc)）。按邮箱域名自动入组有一个安全前提：**只能信任已验证的邮箱**（[Cognito 安全建议](https://docs.aws.amazon.com/cognito/latest/developerguide/multi-tenancy-security-recommendations.html)）。子域名、租户代码只是「预选」提示，认证本身不需要它们。另外，Auth0 Organizations **不支持按组织的自定义登录域名**（[Auth0](https://auth0.com/docs/manage-users/organizations/organizations-overview)）。

**token 里只放当前一个组织**是各家一致的做法，切换组织就重新签发。

| 产品 | 账号归属 | access token 里的租户 claim | 切换方式 |
|---|---|---|---|
| Auth0 | 多组织 | `org_id`（可选 `org_name`），`permissions` 只含当前组织的角色权限 | 带 `organization` 重新走 /authorize（社区做法：`prompt=none` 静默认证，二手） |
| WorkOS | 多组织 | `org_id` + `role` + `permissions` | 用 refresh token 认证并传 `organization_id` |
| Clerk | 多组织 | v2 的紧凑 `o` 对象（`id`/`slg`/`rol`/`per`）；v1 顶层 `org_id` 于 2025-04-14 废弃 | `setActive`，每个浏览器标签页各自记住当前组织 |
| Logto | 多组织 | 组织 token 带 `organization_id`；ID token 的 `organizations` 列出全部组织 | refresh token grant + `organization_id` |
| Entra | 每租户一个对象 | `tid`；同一人在不同租户 `oid` 不同 | 每个租户一张 token |

表中出处：[Auth0 tokens](https://auth0.com/docs/manage-users/organizations/using-tokens)、[WorkOS sessions](https://workos.com/docs/authkit/sessions)、[Clerk session tokens](https://clerk.com/docs/guides/sessions/session-tokens)、[Logto](https://docs.logto.io/authorization/organization-level-api-resources)、[Entra claims](https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference)。Auth0 还要求 API 校验 `iss`，把 `org_id` 和已知组织（或请求 URL 里的子域名）比对，并「segment data and resources by org_id」。Clerk 则专门提醒，按组织 ID 过滤「doesn't itself authorize access to a resource」：过滤只是数据范围，授权要另外判断（[Clerk](https://clerk.com/docs/guides/organizations/overview)）。AWS SaaS Lens 的要求类似：租户由一个独立于用户的服务管理，租户记录带 active/inactive 状态，用户属于多个租户时加一步选择，token 里只放必要的租户属性（[AWS SEC 1](https://wa.aws.amazon.com/saas.question.SEC_1.en.html)）。

**唯一性的范围**跟着账号模型走，两种选择各有代价。全局用户派的邮箱或用户名全局唯一，WorkOS 把邮箱 trim、转小写后当唯一键（[WorkOS](https://workos.com/docs/authkit/users-organizations)）。租户池派在租户内唯一：Zitadel 写明「Email addresses can be reused across organizations」，Casdoor 用 `<org>/<username>` 标识用户，Cognito 的 pool-per-tenant 要求「each user must sign up individually for each tenant」（[Zitadel](https://zitadel.com/docs/concepts/structure/users)；[Casdoor](https://casdoor.ai/docs/basic/core-concepts/)；[Cognito](https://docs.aws.amazon.com/cognito/latest/developerguide/bp_user-pool-based-multi-tenancy.html)）。租户内唯一的代价是同一个人有多个账号，日后合并要走 Auth0 式的账号关联，而且两边都必须验证，否则「can allow malicious actors to access legitimate user accounts」（[Auth0 linking](https://auth0.com/docs/manage-users/user-accounts/user-account-linking)）。全局唯一的代价是租户管理员不能「新建」一个已存在的邮箱，只能邀请。ABP 的 Shared User Accounts 把这个后果写得最清楚：开启「一个账号多租户」后，用户名和邮箱全局唯一，锁定、密码策略、2FA「live at the host level」，租户管理员只能把人移出本租户，不能删除或锁定账号。注意这个模式是 ABP **商业版**功能（[ABP Shared User Accounts](https://abp.io/docs/10.7/modules/account/shared-user-accounts)）。

**平台管理员和租户内角色在主流做法里分层**。Zitadel 把实例级 `IAM_OWNER` 等和组织级 `ORG_OWNER` 等分成两套角色，只有实例级管理员能跨组织看用户，「代入」他人还有单独的 impersonator 角色（[Zitadel administrators](https://zitadel.com/docs/guides/manage/console/administrators)）。Casdoor 用一个保留的 `built-in` 组织，「Every user of the built-in organization is a global administrator」（[Casdoor](https://casdoor.ai/docs/basic/core-concepts/)）。ABP 用 `TenantId == null` 表示 host（[ABP](https://abp.io/docs/latest/framework/architecture/multi-tenancy)）。角色定义的主流是「全局定义一次，在每个组织的成员关系上授予」。Clerk 的角色和权限在应用级定义；Logto 的 organization template 明确**不能为单个组织定制角色**（[Clerk](https://clerk.com/docs/guides/organizations/overview)；[Logto template](https://docs.logto.io/authorization/organization-template)）。租户自定义角色还算进阶能力，Auth0 的 Organization roles 当时还在 Early Access（[Auth0 member roles](https://auth0.com/docs/manage-users/organizations/configure-organizations/add-member-roles)）。最后一点和本项目直接相关：Azure 把自建 IdP 列为反模式，原文是「Building your own IdP is complex, expensive, and challenging to secure. It's considered an antipattern」（[Azure Identity](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/identity)）。rust-idm 正属于这一类。

## 单实例上共享表是默认答案，RLS 只当兜底

AWS 把 PostgreSQL 多租户分成三种模型：silo（每租户一个实例）、bridge（每租户一个 database 或 schema）、pool（共享表）。AWS 认为 bridge「suffers from the same noisy neighbor and tenant performance isolation concerns as the pool model」（[AWS bridge，摘要](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/bridge.html)）。各家对规模的判断差异很大，但方向一致。Citus 认为 schema-based 适合 **1–10k** 个租户，row-based 适合 **100–1M+**，原因之一是每个进程各有一份 catalog cache，表多了内存吃紧（[Citus 12](https://www.citusdata.com/blog/2023/07/18/citus-12-schema-based-sharding-for-postgres/)）。PlanetScale 在 2026-04 写道，schema-per-tenant 和 database-per-tenant 都「likely won't scale beyond a few hundred tenants」，每个 database 还有约 8 MB 的模板开销（[PlanetScale](https://planetscale.com/blog/approaches-to-tenancy-in-postgres)）。Neon 推荐的是 project-per-tenant，「generally」不推荐 schema-per-tenant，认为共享表是合理的起点（[Neon](https://neon.com/docs/guides/multitenancy)）。几百和一万这两个上限差了两个数量级，都来自厂商博客，没有可复现的基准，所以本报告只采信方向，不采信数字。

在单机上，判断的关键是 Azure 的一句话：这三种模型的**备份都是整机的**，恢复单个租户要先把备份恢复到一台新服务器，再把这个租户的数据拷回去（[Azure PostgreSQL multitenant](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/service/postgresql)）。database-per-tenant 的主要卖点（按租户 PITR、独立资源）要靠 Neon 这类「每租户一个项目」的平台才能兑现。在单个实例上，它反而要付出「每个库一个连接池」和「每个租户跑一遍迁移」的成本：PgBouncer 和 Neon pooler 的池都按 user × database 划分（[Neon pooling](https://neon.com/docs/connect/connection-pooling)）。schema-per-tenant 还有一个隔离缺陷，PlanetScale 的原话是「There is no database-level enforcement of preventing access to the wrong schema」（[PlanetScale](https://planetscale.com/blog/approaches-to-tenancy-in-postgres)）。连 Rails 生态的 schema 派维护者也在后退。ros-apartment v4 改为按租户建连接池，不再在共享连接上切 search_path，并在 README 里警告「PgBouncer in `transaction` pooling mode can silently serve one tenant another tenant's data」（[ros-apartment](https://github.com/rails-on-services/apartment)）。共享表模式也有自己的弱点：删除单个租户会产生大量 dead tuple，要么等 vacuum，要么按租户分区后直接 drop 分区（[PlanetScale](https://planetscale.com/blog/approaches-to-tenancy-in-postgres)）。

AWS 认为 pool 模型下「Row-level security (RLS) is required」（[AWS FAQ，摘要](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/faq.html)）。RLS 的标准用法由几条硬规则组成，每一条都对应一个会静默失效的坑：

- **连库的角色**：应用要用**非 owner、非 superuser、没有 BYPASSRLS** 的角色连库。超级用户和 BYPASSRLS 角色总是绕过 RLS，表 owner 默认也绕过，除非执行 `ALTER TABLE ... FORCE ROW LEVEL SECURITY`（[PG docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)）。Azure 说得更直白：「don't let your application roles own the tables that they query. Otherwise, a routine permission change can remove your tenant isolation boundary without any visible error」（[Azure PostgreSQL](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/service/postgresql)）。
- **策略写法**：USING 和 WITH CHECK 都要写；开了 RLS 但没有策略的表默认拒绝一切访问。
- **唯一约束**：「Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security」。全局唯一索引会通过 duplicate key 报错泄露别的租户是否有某个值，所以要改成 `(tenant_id, col)` 唯一（[PG docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)；[Bytebase](https://www.bytebase.com/blog/postgres-row-level-security-footguns/)）。
- **怎么传租户**：在**显式事务里**执行 `set_config('app.tenant_id', $1, true)`。第三个参数为 true 时，值「will only apply during the current transaction」，而且这个函数可以绑定参数，不必拼字符串（[PG functions-admin](https://www.postgresql.org/docs/current/functions-admin.html)）。会话级 SET 会留在物理连接上，连接被复用时串到下一个租户（[sqlx #2783](https://github.com/launchbadge/sqlx/discussions/2783)）。反过来，在事务外执行 SET LOCAL 只会报一个 WARNING，设置不生效（二手：[DEV](https://dev.to/qays_kadhim_c3fea1c94957f/the-set-local-advice-is-right-and-it-understates-the-problem-1f62)）。
- **没设租户时**：要 fail closed。Svix 的辅助函数在未设置时返回 -1，于是一行都看不到，「误用普通连接只会让功能坏掉而不会泄露」。Svix 的技术栈正是 Rust（[Svix](https://www.svix.com/blog/row-level-security-defense-in-depth/)）。
- **性能**：给 tenant_id 建索引，而且它必须是 btree 的**前导列**；把 `current_setting` 包进 `(select ...)`，让每条语句只算一次（[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)）。

RLS 不是完整的安全边界。stancl/tenancy v4 自动生成 RLS 策略，却在文档里写明它「not a security boundary」：没有策略的表不受限，级联删除、外键检查、TRUNCATE 都会绕过（[Tenancy v4 RLS](https://v4.tenancyforlaravel.com/postgres-rls/)）。PostgreSQL 自己也出过 RLS 绕过漏洞，例如 CVE-2024-10976（子查询下的 RLS 忽略 user ID 变化，17.1 / 16.5 / 15.9 修复），所以要跟进 minor 版本（[PG security](https://www.postgresql.org/support/security/)）。公开事故里更常见的是「忘了加隔离」和「连接复用串号」，而不是内核 bug。Lovable 生成的 Supabase 项目有约 170 个存在未开 RLS 的表（CVE-2025-48757，二手报道：[case study](https://github.com/boxed-dev/vibe-coding-security/blob/main/free-case-studies/cve-2025-48757-lovable-rls.md)）。ChatGPT 2023-03 的事故是连接池里被污染的 Redis 连接把别的用户的数据返回给当前用户（[BleepingComputer](https://www.bleepingcomputer.com/news/security/openai-chatgpt-payment-data-leak-caused-by-open-source-bug/)），和「池化连接上残留会话变量」是同一类根因。

Rust 生态在这方面很薄。sqlx 的「Strategies for multi-tenancy」讨论从 2023-09 起一直没有维护者答复，社区结论是「每个请求一个事务，事务里 `set_config(..., true)`」（[sqlx #2783](https://github.com/launchbadge/sqlx/discussions/2783)）。最接近现成方案的 crate 是 **tenaxum 0.2.0**（axum 0.8 + sqlx 0.8，用 task-local 传租户，启动时审计 RLS），但它的 HTTP 路径是在**借出连接时设会话级 GUC、归还时重置**，作业路径才用 SET LOCAL（[docs.rs/tenaxum](https://docs.rs/tenaxum/latest/tenaxum/)）。

对象存储方面，AWS 给出两种做法。一是共享桶 + 租户前缀，「scales well when you have hundreds of unique datasets」，但加密、版本控制等是桶级设置；二是每租户一个桶，权限和成本归集简单，默认配额 10,000 个桶（[S3 bucket patterns](https://docs.aws.amazon.com/AmazonS3/latest/userguide/common-bucket-patterns.html)；[S3 quotas](https://docs.aws.amazon.com/AmazonS3/latest/userguide/BucketRestrictions.html)）。真正把隔离兜住的是策略，不是路径拼接。MinIO 支持 `${aws:username}`、`${jwt:sub}` 等策略变量，可以把凭证限定在 `bucket/<前缀>/*` 下（[MinIO AIStor](https://docs.min.io/enterprise/aistor-object-store/administration/iam/access/)）。但 OIDC 场景下只能用固定的一组 jwt claim，任意自定义 claim 不行（[minio #17164](https://github.com/minio/minio/discussions/17164)）。还要注意一个外部变化：多篇二手报道称 MinIO 社区版在 2025-10 停发预编译镜像、2025-12 进入维护模式，仓库随后被归档（[vonng](https://vonng.com/en/db/minio-is-dead/)；[linuxiac](https://linuxiac.com/minio-ends-active-development/)）。

## 主流框架怎么传租户：入口解析一次，跨进程显式带上，缺租户就失败

各框架的共同形态是：在**入口解析一次**租户，写入执行流局部的环境上下文，所有下游基础设施都从它读。ABP 的解析器链里，第一个是从已认证用户的 claims 取租户（`CurrentUserTenantResolveContributor`，文档称之为「the first contributor for the security」），之后才轮到 query、route、header、cookie（[ABP](https://abp.io/docs/latest/framework/architecture/multi-tenancy)）。这意味着已登录请求以 token 为准，客户端可控的来源只是补充。Finbuckle 把当前租户放进 `AsyncLocal`，一个 scope 内「can only be set once」（[Finbuckle](https://www.finbuckle.com/MultiTenant/Docs/CoreConcepts)）。Rails 用 `CurrentAttributes`，Hibernate 把租户钉在 Session 上，换租户就开新 Session（[acts_as_tenant](https://github.com/ErwinM/acts_as_tenant)；[Hibernate](https://raw.githubusercontent.com/hibernate/hibernate-orm/main/documentation/src/main/asciidoc/userguide/chapters/multitenancy/MultiTenancy.adoc)）。跨进程边界一律把租户 ID 序列化进消息：ABP 的分布式事件写进 `ExtraProperties` 头，stancl 的 `QueueTenancyBootstrapper`「Adds the tenant ID to job payloads」（[ABP OutgoingEventInfo](https://github.com/abpframework/abp/blob/dev/framework/src/Volo.Abp.EventBus.Abstractions/Volo/Abp/EventBus/Distributed/OutgoingEventInfo.cs)；[stancl bootstrappers](https://tenancyforlaravel.com/docs/v3/tenancy-bootstrappers)）。缓存 key 一律加租户前缀，并留一个显式的「全局共享」退出口，例如 ABP 的 `[IgnoreMultiTenancy]`（[ABP Caching](https://abp.io/docs/latest/framework/fundamentals/caching)）。周期性后台任务默认在 host 上下文里运行，要自己遍历租户（ABP 支持论坛，二手：[#9458](https://abp.io/support/questions/9458/Is-BackgroundWorker-Tenant-Safe)）。

兜底的方向在 2026 年很明确：从 fail-open 转向 **fail-closed**。Finbuckle v11 在没有租户时「return no rows rather than all rows」（[Finbuckle EF Core](https://www.finbuckle.com/MultiTenant/Docs/EFCore)）。Basecamp 的 activerecord-tenanted 抛 `NoTenantError`（[GUIDE](https://github.com/basecamp/activerecord-tenanted/blob/main/GUIDE.md)）。acts_as_tenant 提供 `require_tenant`（[acts_as_tenant](https://github.com/ErwinM/acts_as_tenant)）。老库还是 fail-open：django-multitenant 原文是「If the current_tenant is not set, then the default/native API without tenant scoping is used」（[django-multitenant](https://github.com/citusdata/django-multitenant)）。所有 ORM 层的自动过滤都有同一个盲区：**原生 SQL 不受约束**。acts_as_tenant 列出 `find_by_sql`、`update_column(s)`、`upsert_all`；Hibernate 列出原生 SQL、存储过程、JDBC。「默认租户」这件事，ABP 提醒过：设了 `FallbackTenant` 后「no way to switch to the host side」（[ABP](https://abp.io/docs/latest/framework/architecture/multi-tenancy)）。也就是说，回退会吞掉「没有租户」这个状态。sqlx 本身就是原生 SQL，没有 ORM 拦截层可以依靠，所以 baserust 的应用层只能靠「仓储签名强制传租户」，数据库层只能靠 RLS。RLS 在这个技术栈里的价值比在 ORM 栈里更高。

## 运维的共识：停用可恢复、删除有延迟、审计记录不随租户删

Azure 把商业状态和技术状态分开建模，技术状态按 provisioning → active → restricted → deactivated → offboarded 推进。Suspended 对应 Deactivated，含义是「Block new activity while preserving data」。状态转换要「tolerate duplicate, delayed, and out-of-order events」。offboard 时，**即使删了业务数据，计费、计量、权益和审计记录也要保留**（[Azure Tenant life cycle](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenant-life-cycle)）。停用成员时，主流做法是立即作废会话。WorkOS 停用 membership 会 revoke 所有活动会话（[WorkOS](https://workos.com/docs/authkit/users-organizations)）。Slack 停用成员会让他「signed out of your workspace(s) on all devices」，但消息保留（[Slack](https://slack.com/help/articles/204475027)）。删除都留有反悔期：Linear 删除工作区排在 **48 小时**后执行，期间任何管理员都能取消（[Linear](https://linear.app/docs/workspaces)）；GitHub 移除成员后数据保留 3 个月，删除组织后组织名 **90 天**内不能被重新注册（[GitHub](https://docs.github.com/en/organizations/managing-organization-settings/deleting-an-organization-account)）。Azure 建议**禁止复用租户标识**，用来防止子域名接管（[Azure Domain names](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/domain-names)）。

限流和观测都以租户为主键。Slack 的 Web API 限流按「per API method per workspace/team per app」计，超限返回 429 + `Retry-After`（[Slack rate limits](https://docs.slack.dev/apis/web-api/rate-limits)）。Azure 的 noisy neighbor 指南要求把租户 ID 写进每次请求的遥测，按租户聚合资源用量，并对客户公开限流规则（[Azure Noisy Neighbor](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/noisy-neighbor/noisy-neighbor)）。AWS 建议用公共库提供「tenant-aware logging wrapper」，不让业务代码手写租户字段（[AWS SEC 1](https://wa.aws.amazon.com/saas.question.SEC_1.en.html)）。审计日志的样板是 GitHub：保留 **180 天**，只有 owner 能看，字段有 `action`（`category.operation` 形式）、`actor`、`user`、`org`、`created_at`（[GitHub audit log](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization)）。

域名分三档：不用域名（租户来自 token）、子域名配通配 DNS 和通配证书、客户自定义域名。自定义域名要用 CNAME 或 TXT 随机值验证所有权，以防「parking」别人的域名；解约后要先删 CNAME 才能移除，否则会留下悬空 DNS（[Azure Domain names](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/domain-names)）。单机自托管时，Caddy 的 On-Demand TLS 能在首次握手时签证书，但「must be both enabled and restricted to prevent abuse」：签之前先通过 `ask` 端点查域名是否已验证（[Caddy](https://caddyserver.com/docs/automatic-https)）。无论用哪种域名方案，都要校验「域名推出的租户等于 token 里的租户」（[Auth0](https://auth0.com/docs/manage-users/organizations/using-tokens)）。从单租户迁移过来，唯一能找到的官方步骤来自 Citus：加列时保持全库类型一致，从父表 join 取值**分批回填**（「Doing the whole table at once may cause too much load」），用 pg_cron 追平（[Citus migration](https://docs.citusdata.com/en/stable/develop/migration_mt_schema.html)）。之后加 NOT NULL、把主键和唯一键改成含 tenant_id 的复合键，这部分只见于搜索摘要。「先建一个默认租户承接存量数据」只有社区经验文章，没有官方背书（[dev.to](https://dev.to/neojuridico/migrating-a-single-tenant-saas-to-multi-tenant-workspaces-with-ef-core-global-query-filters-396o)）。

## 落到 baserust：租户身份放 idm，账号按多对多建模，数据用共享表 + RLS

### 先核对现状：哪些已经就位，哪些会坑

下表是本次直接读代码确认的事实，不是推断。

| 现状 | 出处 | 对多租户的含义 |
|---|---|---|
| `users.username`、`users.email` 在存活行上**全局唯一** | `rust-idm/migrations/0001_init_idm.up.sql` | 已经是「全局账号」的形状，天然适合成员关系模型 |
| `roles.name` 全局唯一；`user_roles(user_id, role_id)` 不带租户 | `rust-idm/migrations/0002_add_roles.up.sql` | 现有角色语义就是「平台级」 |
| `sessions` 不带租户列；access TTL 900 秒，refresh 7 天 | `0001_init_idm.up.sql`；`baserust/.env.example` | 切换租户、按租户撤销都需要扩展；停用生效的上限是 15 分钟 |
| `TokenClaims` 有 `roles`，签发端可拔插，注释写明「app 可注入自定义 claims(tenant_id/权限位…)」 | `rust-idm/src/token.rs` | 加租户 claim 不用改验签结构 |
| 每个 schema 一个同名 role，`create schema ... authorization <role>`，迁移和运行用同一个 role | `baserust/scripts/initdb/00-roles-schemas.sh`；`baserust/justfile` | **运行时 role 就是表的 owner**，RLS 默认对它不生效 |
| `content.tenant_id uuid not null`，有 `(owner_id, tenant_id)` 索引；`list` 按租户过滤，但 `get_content` 注释写「**不**强制 tenant —— 鉴权归 app 授权层」 | `rust-content/migrations/0001_init_content.up.sql`；`rust-content/src/service.rs` | 按 ID 取单条是潜在的跨租户越权访问（IDOR）入口 |
| object_key 默认是 `{content_id}/{uuid}`，不带租户前缀 | `rust-content/src/service.rs` | 对象存储层没有租户边界 |
| 事务约定：「原子单元 = 一个 trait 方法，Tx 不进签名」 | `rust-content/CLAUDE.md`；`baserust/CLAUDE.md` | 每个仓储方法要在自己开的事务里设租户上下文 |

### 问题一：租户身份放 idm，租户的业务配置放 app

**文档支持的事实**：Azure 给出两种放法，一是身份和授权全放 IdP，二是「凭据放 IdP，租户角色和权限放应用层、和租户信息放在一起」（[Azure Identity](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/identity)）。AWS 要求租户上下文随 JWT 流过所有服务，「不需要再往返另一个服务」去查（[AWS SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/identity-and-access-management.html)）。ABP 在身份模块里管「用户 ↔ 租户」，在租户管理模块里管租户元数据（[ABP](https://abp.io/docs/latest/framework/architecture/multi-tenancy)）。Azure 还要求权益（entitlements）不要从角色推断（[Azure Identity](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/identity)）。

**推断与我们的取舍**：baserust 的硬约束是「app 只验 JWT，不查 idm 库」，又禁止跨 schema join。按 Azure 的第二种放法，把成员关系放在 app，就意味着 token 里的租户只是用户自选的值，app 每个请求都要回自己的库查一次成员关系，这等于放弃了「token 即授权上下文」。所以建议在 idm 里新增三样东西：

- `tenants` 表：`id`、`slug`、`status`、`delete_after`；
- `memberships` 表：`tenant_id`、`user_id`、`status ∈ {pending, active, inactive}`；
- `membership_roles` 表：`tenant_id`、`user_id`、`role_id`。

登录、切换租户、刷新 token 时，idm 校验「租户 active 且成员关系 active」再签发。app 里放 `tenant_settings`、品牌、权益这类业务配置，按 `tenant_id` 字符串关联，不加外键，这和现有的「引用用标识非 FK」一致。

租户被停用后，app 要能尽快感知，同时又不能查 idm 库。可以复用现成的 outbox → NATS 管道：idm 发出 `tenant.status_changed` 事件，app 把它投影成自己 schema 里的租户状态表，中间件在每个请求上查这张表（带几秒缓存）。这样停用的生效时间从「access TTL 上限 15 分钟」缩短到秒级。这条依据的是本仓库已有的 outbox 和 search 投影机制，业内文档没有直接对应的做法。

### 问题二：按多对多建模，产品上可以先限制一人一租户

**文档支持的事实**：新一代 IdP 和主流 B2B 产品全部是多对多（见第一节）。只要支持多组织，access token 就只带一个当前组织，切换时重签。WorkOS 和 Logto 都是「用 refresh token + 目标组织换新 token」，不需要重新输入密码（[WorkOS sessions](https://workos.com/docs/authkit/sessions)；[Logto](https://docs.logto.io/authorization/organization-level-api-resources)）。一对一模型的代价是同一个人加入第二个组织就得注册第二个账号（[Cognito](https://docs.aws.amazon.com/cognito/latest/developerguide/bp_user-pool-based-multi-tenancy.html)）。ABP 默认是一对一（Isolated），多对多（Shared）是后来加的商业功能，开启后唯一性和安全策略都要上移到平台级（[ABP Shared](https://abp.io/docs/10.7/modules/account/shared-user-accounts)）。

**推断与我们的取舍**：rust-idm 的用户名和邮箱**已经是全局唯一的**，所以「一对一 + 租户内唯一」反而要倒退改索引。多对多只需要新增一张成员关系表。一对一是多对多的特例：在 `memberships(user_id)` 上加一个可配置的唯一约束就能退化。反方向的迁移要改数据和 token 格式，代价大得多。

建议的 claim 形状如下。`roles` 保留现有含义，作为**平台角色**（来自 `user_roles`）。新增 `tenant_id`（当前租户）和 `tenant_roles`（当前租户内的角色，来自 `membership_roles`）。不把全部租户放进 access token。

登录流程：认证成功后，0 个成员关系时，平台管理员进入平台上下文，其他人报错或引导创建；1 个时直接进入；多个时返回 WorkOS 式的「待选择」响应，或者默认进入上次使用的租户。切换走 idm 的 `POST /auth/switch-tenant` 接口，并给 `sessions` 加 `tenant_id` 列，使刷新 token 时沿用同一租户，也能按租户批量撤销会话。

平台管理员采用 Zitadel 式的「作用域分层角色」，不做 Casdoor 式的系统组织。进入某个租户时要显式切换并写审计，不能让平台角色绕过租户过滤。

全局账号有一个必须预先定死的权限边界：租户管理员只能**邀请**已有账号、把人**移出**本租户，不能改密码、锁定或删除账号。这和 Keycloak 的 unmanaged member、ABP Shared 的规则一致（[Keycloak members](https://github.com/keycloak/keycloak/blob/main/docs/documentation/server_admin/topics/organizations/managing-members.adoc)）。

### 问题三：共享表 + 仓储显式传租户 + RLS 兜底，先修 role 和 nil 两个坑

**文档支持的事实**：单实例上 schema/database-per-tenant 的成本和收益见第二节。RLS 要求非 owner 连接、FORCE、事务级 `set_config`、复合唯一键（[PG docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)；[Azure PostgreSQL](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/service/postgresql)）。Svix 在 Rust 生产环境里就是这样做的，并且 fail closed（[Svix](https://www.svix.com/blog/row-level-security-defense-in-depth/)）。owner 永远可以改策略或关闭 RLS（[PG docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)）。

**推断与我们的取舍**：

第一，拆分 role。每个 schema 分成 owner（如 `app_owner`，只用来跑迁移）和运行时 role（`app`，只授 DML，不是 owner，没有 BYPASSRLS）。现在 initdb 脚本和 justfile 用的是同一个 role，不拆的话 FORCE 也挡不住「一次权限调整就让隔离消失」。如果平台级跨租户查询确实需要，单独开一个连接池。

第二，在仓储方法里设上下文。这正好契合现有的事务约定：既然 Tx 不进签名，就让每个读写租户数据的仓储方法**显式接收 `TenantId`**，在方法内开事务，第一句执行 `SELECT set_config('app.tenant_id', $1, true)`，SQL 里同时写 `WHERE tenant_id = $1` 走索引快路径。RLS 只负责兜住漏写的 WHERE。策略写成 `tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid`，没设置就看不到任何行。不建议照搬 tenaxum 的「借出连接时设会话级 GUC」，以免日后加 PgBouncer 时串租户。

第三，处理 nil。`TenantId` 做成 newtype，构造时拒绝 `Uuid::nil()`；迁移时建一个**固定 UUID 的真实默认租户**，把 `content.tenant_id` 从 nil 回填过去，再加 `CHECK (tenant_id <> '00000000-0000-0000-0000-000000000000')`。原因是：如果 nil 被当作「默认租户」，任何「取不到租户就用 nil」的代码都会静默写进同一个租户，这正是 ABP `FallbackTenant` 警告的问题。

第四，补齐其他入口。`get_content` 这类按 ID 取单条的方法要带租户条件，跨租户访问返回 404（和 baserust 的 authorization skill 的「403 vs 404」口径对齐）；业务表的唯一键改成 `(tenant_id, …)`；search 投影、outbox 事件、后台任务的消息体都要带 `tenant_id`；CI 里加两类检查，一是「租户 A 的 token 访问租户 B 的资源 ID 返回 404」的黑盒测试，二是启动或 CI 时审计「每张有 tenant_id 的表都 ENABLE + FORCE 并且有策略」，参照 tenaxum 的 `audit::ensure_isolation` 思路。

第五，对象存储用单桶 + `tenants/{tenant_id}/{content_id}/{uuid}` 前缀，由后端签名并校验对象归属。按租户下发受限凭证的 MinIO 策略可以以后再做。MinIO 社区版的维护状态值得单独立项评估，本次调研没有核实替代品。

### 其余配套的最小集合

以下全部是推断，依据见第四节。租户状态最小集取 `provisioning / active / suspended / pending_deletion / deleted`，删除按「软删 + 延迟硬删」处理，延迟期可参考 Linear 的 48 小时到 GitHub 的 90 天；slug 不复用，或者设冷却期。在认证中间件里把 `tenant_id`、`user_id` 写进 tracing 的根 span。现有的「系统监控」页如果要加租户维度，要限制基数，只看 top-N，这符合 observability skill 里「统计键只许闭集」的规则。审计表参照 GitHub 的字段，审计行不随租户数据删除。限流键用 `(tenant_id, 路由类别)`，超限返回 429 + `Retry-After`。域名先只靠 token 识别租户。要上自定义域名时，现在对外只开 nginx:80，需要加一个 Caddy 这类能用 `ask` 端点控制按需签证书的入口，这会多一个组件。

## 结论

这次调研最大的修正是：真正决定隔离强度的，不是「共享表还是分 schema」，而是**租户上下文的权威来源在哪里，以及缺失时默认怎么处理**。业内把权威来源统一放在签发 token 的那一侧（claims 优先于 header），把缺失时的默认改成 fail-closed。照这个标准看 baserust，隔离模型的选择几乎没有争议，真正的风险是两个现成的默认：运行时 role 拥有表，以及 nil 被当成租户值。两者都会让隔离在没有报错的情况下失效。另一个反直觉的地方是，sqlx 没有 ORM 拦截层，RLS 在这个技术栈里比在 Rails/EF 栈里更值得上；而 baserust 现有的「一个原子单元 = 一个 trait 方法」约定，恰好让事务级 `set_config` 有了天然的落点。

真正难以回头的决定只有两个：**账号唯一性的范围**和 **token 里租户 claim 的形状**。rust-idm 已经是全局唯一，所以趁现在把 claim 定成「单个当前租户 + 平台角色与租户角色分开」，把成员关系建成多对多，其余都可以分期做。还有两件需要知情的事：rust-idm 本身属于 Azure 所说的自建 IdP 反模式，SSO 联邦、SCIM、风险检测以后都要自己补；MinIO 社区版的维护状态会影响对象存储层的长期选型。两者都不阻塞多租户落地，但应该作为独立议题排期。
